The workloads

Every workload is uniform random: each operation picks its key uniformly at random, with no hot set. Inserts draw new keys in a scrambled order, so they also land uniformly across the key space.

Read
GET of a uniformly random existing key. In memory rows serve every GET from the Document Cache; on disk rows turn it off, so each GET goes through the index to the data on disk.
Insert
SET of a new key, added on top of the preloaded data, so the store grows during the run.
Overwrite
SET of a uniformly random existing key, replacing its value. The store stays the same size and compaction reclaims the old versions.
Non-blind write
The SET first looks up the existing key, which costs an index read.
Blind write
The SET is written without looking up the old value.
Durable
A SET is acknowledged once the shared write-ahead log reports it persisted. Non-durable SETs are acknowledged before that.
Document Cache
The fluxkv server's in-memory cache of whole documents (key and value), in front of magma and its block cache.

At 8 B the per-key overhead (seq record, key index entry, metadata) is several times the 20 B payload, so both figures grow. Blind 8 B overwrites reach {{sa18}}× space because their garbage is only found by compaction.

Residency: how much of the data fits in memory

Memory is the 16 GiB quota (direct IO), 10.9 GB of it block cache; in-memory rows add a 32 GiB Document Cache. The index is {{idx}} GB at 100M keys.

Index residency: one dataset, less memory

100M keys × 1 KB, the same data in every row; only the block cache shrinks (--write-cache-ratio). Memory per key is block cache ÷ 100M keys.*

What was run, and how

Two value sizes, each with two read rows and eight write rows (insert or overwrite × durable or not × blind or non-blind). Each throughput row T has a latency row L paced from its result, plus four two-hour S rows. All keys are 12 B, uniform, in scrambled order, with a 1 KB seqIndex block.
