Blind
The SET is written without looking up the old value

Acknowledged once the shared write-ahead log has it on disk

How much of the index fits in the block cache

Before you compare

  • One run per row. The same build on different boxes varies by up to 5%.
  • One box per row, client over loopback: these are single-box ceilings with no network.
  • Flags: overloaded reached under 95% of its target rate, p99 ≥ 1 s a multi-second tail, client-bound limited by the latency client.
  • RSS uses jemalloc's defaults, which hold about 2 GB of unreturned memory.

Space amp = bytes on disk ÷ (keys × (12 B + value)). Write amp = device bytes written ÷ bytes the server received. At 8 B the per-key overhead (seq record, key index entry, metadata) is several times the 20 B payload, so both grow; blind 8 B overwrites reach {{sa18}}× space because their garbage is only found by compaction.

The workloads

Uniform random
Every operation picks its key uniformly at random, with no hot set. Inserts draw new keys in a scrambled order, so they also land uniformly.
Read
GET of an existing key. In memory rows serve every GET from the Document Cache; on disk rows turn it off, so each GET goes through the index to the data on disk.
Insert
SET of a new key on top of the preloaded data, so the store grows during the run.
Overwrite
SET of an existing key. The store stays the same size and compaction reclaims the old versions.
Document Cache
fluxkv's in-memory cache of whole documents, in front of magma and its block cache.

Method64 rows · T / L / S / E

What was run, and how

Two value sizes, each with two read rows and eight write rows (insert or overwrite × durable or not × blind or non-blind). Each T row has an L row paced from its result, plus four two-hour S rows and the E residency rows. All keys are 12 B, uniform, in scrambled order, with a 1 KB seqIndex block.
